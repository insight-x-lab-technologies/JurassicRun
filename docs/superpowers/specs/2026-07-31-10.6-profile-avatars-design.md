# 10.6 — Avatares de perfil (design)

**Item:** Fase 10, Frente B, item 10.6 (`docs/roadmap/PHASE-10-polish-and-portrait.md`).
**Data:** 2026-07-31. **Toca `src/core/`:** não. **Determinismo:** inalterado (73).

## Problema

O avatar do jogador é gerado: `avatarFor(profile)` devolve `{ initial, hue }` e a UI desenha um
disco `hsl(hue, 55%, 45%)` com a inicial do nome (`ProfileScreen.tsx:9`, `HomeScreen.tsx:38` — o
mesmo componente copiado em duas telas). É a "bola vermelha" do relato do usuário: identidade
pobre, sem escolha, e destoante da arte AAA das outras telas.

## Decisão de produto (travada no arquivo da fase)

Grade de avatares **pré-criados**, não upload. Motivo já registrado: quota do `localStorage`
(~5 MB para tudo), privacidade/moderação e coerência de arte. O sub-item **10.6b (upload de foto)
fica fora**: a grade resolve o pedido e o upload traria bytes de usuário para dentro do storage que
a 10.3 acabou de limpar.

## Escopo entregue

1. Catálogo de **12 avatares** (`a01`…`a12`), puro, em `src/services/profile/avatars.ts`.
2. `Profile.avatarId` **obrigatório no tipo**, com backfill determinístico na leitura do storage.
3. Seletor na tela de Perfil; avatar escolhido reflete na Home, no cartão de identidade e na lista
   de jogadores.
4. Arte **placeholder procedural** (12 medalhões) gerada por script, com asset-spec do conjunto
   real e a entrada de pipeline documentada para quando a arte AAA dropar (REGRA 2 e REGRA 5).
5. `avatarId` passa a ser o valor sincronizado na coluna `players.avatar` do Supabase.

## Arquitetura

### Catálogo puro — `src/services/profile/avatars.ts`

```ts
export const AVATAR_IDS = ['a01', …, 'a12'] as const;
export type AvatarId = (typeof AVATAR_IDS)[number];
export interface AvatarDef { readonly id: AvatarId; readonly hue: number }
export const AVATARS: readonly AvatarDef[];              // 12, hues espaçados 30°
export function isAvatarId(v: unknown): v is AvatarId;
export function defaultAvatarId(profileId: string): AvatarId;      // hash(id) % 12
export function resolveAvatarId(raw: unknown, profileId: string): AvatarId; // desconhecido → default
export function avatarDef(id: AvatarId): AvatarDef;
```

`defaultAvatarId` reusa **o mesmo hash** que `avatarFor` já usa (`h = h*31 + charCode`, `>>> 0`):
mesmo perfil ⇒ mesmo avatar inicial em qualquer aparelho, e nenhum perfil antigo "muda de cara" a
cada boot. `avatarFor` **continua existindo** — vira o fallback visual (inicial + matiz) quando o
PNG do avatar não carrega.

O catálogo é do serviço de perfil, **não** do `nest`: reusar `DINO_ROSTER` acoplaria identidade de
jogador a entitlements/traços (mesma armadilha que a 10.7 recusou ao deixar troféus de coleção de
fora). Os 12 ids são um namespace próprio e opaco.

### Modelo e persistência

- `Profile` ganha `readonly avatarId: AvatarId` **obrigatório**: um call site que crie perfil sem
  avatar quebra a compilação (precedente 10.7, `MatchSummary`).
- `createProfile(state, id, name, createdAt)` preenche `defaultAvatarId(id)` — a assinatura não
  muda, o avatar inicial é derivado, não escolhido.
- Novo redutor puro `setAvatar(state, profileId, avatarId): ProfileState`, no molde de
  `renameProfile` (id inexistente ⇒ estado inalterado).
- `profileService.setAvatar(avatarId: AvatarId): boolean` no ativo, commitando via `this.commit`.
- **Storage:** `STORAGE_KEY` continua `jurassicrun.profiles.v1`. Bumpar apagaria os perfis — o
  oposto do requisito (a 10.3 bumpou porque queria descartar; aqui queremos preservar; mesma
  distinção da 10.7). O payload passa a gravar `version: 2`.
- `parseState` **backfilla**: perfil sem `avatarId`, com tipo errado ou com id fora do catálogo
  recebe `defaultAvatarId(p.id)`. Ou seja, `isProfile` não exige o campo; a normalização é que o
  materializa. Efeito: se um avatar for retirado do catálogo no futuro, os perfis que o usavam
  caem no default em vez de renderizar um id morto.

### Render

- Componente compartilhado novo `src/app/components/Avatar.tsx` — a cópia de `HomeScreen` e
  `ProfileScreen` some (as duas telas passam a importar).
- Marcação: `<span class="avatar" style="background-color: hsl(hue,55%,45%)">` contendo
  `<img class="avatar__img" src={BASE_URL}ui/avatar.<id>.png alt="">`. `BASE_URL` via
  `import.meta.env` (mesmo padrão do `navIcon` da Home) — caminho absoluto em CSS quebraria no
  GitHub Pages, que serve sob `BASE_PATH`.
- `onError` no `<img>` ⇒ estado local `failed` ⇒ desenha a inicial (`avatarFor`). Cobre arte
  ausente, storage de imagem bloqueado e id órfão sem quebrar a tela.

### Seletor (tela de Perfil)

- Bloco novo `AvatarPicker` na coluna de ações, acima de "Renomear".
- Semântica: `role="radiogroup"` com `aria-label={t('profile.avatar')}`; cada tile é
  `<button role="radio" aria-checked>` com `aria-label={t('profile.avatarOption', { n })}`.
- Clique chama `profileService.setAvatar(id)`; a assinatura reativa (signals) atualiza Home,
  cartão e lista sem recarregar.
- **i18n:** 2 chaves novas × 10 idiomas — `profile.avatar` ("Avatar") e `profile.avatarOption`
  (`"Avatar {{n}}"`, interpolação já suportada pelo `I18nService.t`). Nomes próprios por avatar
  (12 × 10 = 120 strings) ficam para quando a arte real definir os personagens; hoje seriam nomes
  inventados para 12 medalhões de matiz.

### Online

`src/services/online/index.ts:161` monta `avatar: String(hue)`. Passa a mandar `active.avatarId`.
A coluna `players.avatar` é `text` sem `check` (6.1) ⇒ zero migração, e a chave de identidade
`${id}|${name}|${avatar}` já força o re-upsert quando o jogador troca de avatar. Nenhuma tela
renderiza `playerAvatar` hoje (verificado), então não há regressão visual.

### Arte — placeholder agora, AAA depois (REGRA 2)

- `scripts/gen-avatar-placeholder.mjs` (zero dep, no molde de `gen-app-icon.mjs`): compõe 12
  medalhões 128×128 — fundo radial dos tokens + aro dourado + o pterodáctilo real de
  `public/ui/dino.starter.png` com **rotação de matiz** por índice. Saída: `public/ui/avatar.aNN.png`.
- **Não sobrescreve arquivo existente** (só com `--force`). É a resposta ao gotcha registrado da
  Fase 9: os geradores `gen-{parallax,obstacle}-placeholder` apagavam a arte real ao rodar de novo.
- npm script `gen:avatars`. Fora do build; roda sob demanda.
- Asset-spec `docs/assets/specs/ui.avatars.md` + linha no `asset-registry.md`, descrevendo a folha
  real (`public/art/final/ui/ui.avatars.png`, grade 4×3) e a entrada exata a acrescentar em
  `UI_SOURCES` do `gen-ui.mjs` quando ela chegar. A entrada **não** entra agora: `loadArt` lança se
  o arquivo-fonte não existe e quebraria `npm run gen:ui`.
